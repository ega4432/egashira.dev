# コミット前の lint / format / 型チェック

このリポジトリでは pre-commit フック（husky + lint-staged, `.lintstagedrc.js`）が prettier・eslint・`astro check` をステージされたファイルに対して実行し、失敗するとコミットがブロックされる。ユーザーから「commit して」と言われたら、フックに弾かれて手戻りが起きないよう、コミット前に同じ種類のチェックを自分で先回りして通しておく。

## 手順

1. **フォーマットと lint の自動修正を実行する**

   ```bash
   npm run prettier:fix
   npm run eslint:fix
   ```

   これらは自動修正可能な問題（フォーマット崩れ、多くの lint 警告）をその場で直す。実行後、`git diff` で意図しない変更（無関係なファイルの大規模な書き換えなど）が入っていないか軽く目を通す。

2. **型チェックと Astro の静的チェックを実行する**

   ```bash
   npm run astro -- check
   npx tsc --noEmit
   ```

   `npm run build` はこれに加えて `playwright install chromium && astro build` まで実行するため時間がかかる。コミット前の確認としては上記 2 つで十分（pre-commit フックが検証するのも実質この範囲）。ビルド全体の確認が必要な場面（大きな変更、レンダリングパイプラインに触れた場合など）では `npm run build` を案内してよい。

3. **エラーが残っていたら中身を読んで直す**

   `eslint:fix` や `prettier:fix` で直らない lint エラー（`--max-warnings 0` のため警告も 1 件でも残っていれば失敗扱い）や、`astro check` / `tsc --noEmit` の型エラーは自動修正されない。エラーメッセージに出ているファイルとエラー内容を読み、実際にコードを修正すること。修正が完了したら該当するコマンドを再実行し、クリーンになるまで繰り返す。

   ここで安易にエラーを黙らせる方向（`// @ts-ignore` の追加、ESLint ルールの無効化、`--no-verify` でのコミット強行など）に逃げない。原因を理解して直すか、直せない・直すべきでない事情がある場合はユーザーに判断を仰ぐ。

4. **全て通ったらコミットする**

   通常のコミット手順（`git status` / `git diff` / `git log` の確認、変更内容に基づくコミットメッセージの作成、関連ファイルの `git add`、`git commit`、コミット後の `git status` 確認）に従ってコミットする。lint/format の自動修正で意図せず変更されたファイルも、意味のある差分であればコミット対象に含める。

## 注意点

- `npm run eslint` と `npm run prettier`（`:fix` なし）はチェック専用で自動修正しない。修正が目的のときは必ず `:fix` 付きのスクリプトを使う。
- `prettier:fix` はリポジトリ全体（`.`）を対象にするため、今回の作業と無関係なファイルまで整形され直すことがある。差分に無関係な変更が大量に含まれる場合は、それが実際に整形漏れの是正なのか、意図しない副作用なのかを確認してからコミットする。
- ユーザーが明示的に「lint/format のチェックは飛ばしてコミットして」のように指示した場合はこの限りではないが、その場合でも `--no-verify` で pre-commit フックをスキップすることはしない（フックが失敗する具体的な理由があるなら、それを解消するのが筋）。
